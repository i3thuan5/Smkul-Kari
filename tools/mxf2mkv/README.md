# mxf2mkv

把本機一個資料夾底下的 `.mxf` 母帶逐支轉成封存 mkv，**轉完一支就上傳 SFTP**，遠端目錄結構照著來源擺。

給隨身硬碟用的：插上去、跑完、拔掉。它不查節目目錄、不查 `smkul.csv`、不查 inventory，所以還沒登記的母帶照樣轉得動——哪一支是哪一集，之後再 rename 或 mv。

## 怎麼跑

```bash
python3 -m tools.mxf2mkv --src /media/hong/USB/2月原始mxf檔
```

先試跑看路徑對不對（不會動任何檔案）：

```bash
python3 -m tools.mxf2mkv --src /media/hong/USB/2月原始mxf檔 --dry-run
```

先做兩支試水溫：

```bash
python3 -m tools.mxf2mkv --src /media/hong/USB/2月原始mxf檔 --limit 2
```

需要 `ffmpeg`、`ffprobe`、`sftp`（openssh）。**沒有 Python 套件要裝。**

## 檔案會去哪

```text
隨身硬碟（唯讀，只讀這一次）
  /media/hong/USB/2月原始mxf檔/
   ├── a.mxf
   └── 夜間/b.mxf
        │
        ▼
本機 SSD /tmp/mxf2mkv-<隨機>/      每次執行各自一個，跑完刪掉
        │
        ▼
SFTP  /home/mkv-raw/2月原始mxf檔/   ← 遠端根 ＋ --src 的最後一層資料夾名
   ├── a.mkv
   └── 夜間/b.mkv                   ← 底下相對路徑照抄，只換副檔名
```

跟族語新聞的封存（`/home/news/mkv/`）**完全不相干**：兩邊重複的影片照轉，不互相覆蓋。

## 參數

| 參數 | 預設 | |
|---|---|---|
| `--src` | 必填 | 來源資料夾，會遞迴找底下所有 `.mxf` |
| `--dst-root` | `/home/mkv-raw` | 遠端根目錄 |
| `--work` | `/tmp/mxf2mkv-<隨機>` | 中間產物放哪。每次執行各自一個，所以同時跑 2–3 支不會互相踩 |
| `--report-dir` | `kithann/mxf2mkv` | 紀錄與對照表 |
| `--crf` | `23` | 視訊 CRF |
| `--limit` | `0`（全部） | 只做前 N 支 |
| `--dry-run` | | 只列會做什麼、傳去哪 |

**沒有 `-j`**：來源通常是單顆外接硬碟，同時讀兩支數十 GB 的檔案互相搶 I/O，比逐支慢。要平行的話，對**不同碟上**的來源資料夾各起一個執行。

離開碼：全部成功或跳過是 `0`；有任何一支失敗是 `1`（但仍然跑完全部）。

## 產出在哪、失敗了去哪看

```text
kithann/mxf2mkv/
└── 2月原始mxf檔/                              ← 外層只有來源名，歷次執行放一起
    ├── 0906-1420_2月原始mxf檔.log             每支的 ffmpeg／sftp 錯誤輸出全文
    ├── 0906-1420_2月原始mxf檔.manifest.json   對照表
    ├── 0907-0930_2月原始mxf檔.log             第二次跑，同一個資料夾
    └── 0907-0930_2月原始mxf檔.manifest.json
```

舊檔**絕對不會被覆蓋**；同一分鐘內跑兩次會自動加 `-2`、`-3` 後綴。

有任何一支失敗時，工作目錄**留著不刪**，路徑會印在最後——那是唯一還留著半成品可以看的地方。

對照表每支一筆，其中 `音軌` 那欄是日後要接目錄、要決定拿哪一條音軌做語音辨識時看的：

```json
{
  "audio_tracks_kept": 1,
  "audio_tracks_src": 2,
  "remote": "/home/mkv-raw/2月原始mxf檔/夜間/b.mkv",
  "remote_bytes": 2540000000,
  "seconds": 1180,
  "src": "夜間/b.mxf",
  "src_bytes": 19012345678,
  "音訊逐位元相符": true,
  "結果": "成功",
  "音軌": "兩軌相同，留一軌"
}
```

## 它保證什麼

**音訊逐位元不變。** 這批語料是要拿去訓練聲學模型的，音訊被重新量化就失去價值。編碼時順便算出來源每一條音軌的指紋，再拿封存的指紋去比；對不上就是**失敗**，不是警告，而且不會有東西留在遠端的最終名稱上。

**不會靜靜丟掉音軌。** 來源幾條音軌就處理幾條。只有在兩條**逐位元相同**時才會捨去重複的那條——實測 63 支既有封存，35 支兩軌相同、28 支不同，而雙軌放不同語言（主聲道／國際聲）在廣播界是標準做法，所以「看起來一樣就丟一條」不是這支程式能自己決定的事。

**斷線不會留下看起來完成的檔案。** 上傳先送到 `<名>.mkv.partial`，位元組數對上了才改成 `<名>.mkv`。所以「最終名稱在不在」就是「這支做完了沒有」的答案，重跑時據此跳過。

## 視訊參數為什麼是這樣

CRF 23、`yuv420p`、不縮放不抽幀——這些數字是拿字幕辨識的字元錯誤率量出來的，CRF 18–28 全區間零錯誤，CRF 32 會掉整句字幕。餘裕本身就是目的。完整的實測記錄在 `.claude/skills/video-subtitle-srt/壓縮率分析.md`。

編碼與音軌邏輯跟族語新聞的封存共用同一份程式（`scripts/transcode/encode_master.sh` 與 `scripts/transcode/audio_tracks.py`），所以兩邊做出來的封存是同一種東西。
