## Context

動機與量到的數字見 proposal.md。這裡只補實作要用到的現況與外部限制。

**現況的四個位置**：`scripts/news/vision_tools/prompt.py` 的 `plan(total, size, min_tail)` 拿「張數」切出連續區段 `(lo, hi)`，`brief()` 對 `sorted(sheets)`（全部組合圖）取第 N 段，判準用 `{first}`–`{last}` 兩個檔名表示範圍；`scripts/news/batches.py` 的 `spans()` 轉呼叫同一支，但它餵進去的是 `pending_sheets()`（排掉 `verified.json` 已核實的），而且 `bNN.tsv` 的編號從 `made = 1` 重新算起；`scripts/ocr/sheets.py` 的 `_block_size()` 與 `flush_sheet()` 各有一處 `tile.height + 2`，是圖條與圖條之間的分隔；`sheets.json` 的格式是 `{組合圖檔名: [cue 編號…]}`，有五支程式在讀（`ingest.py`、`prompt.py`、`ocr/cli.py`、`split_cue.py`、`reread_tools/regen_strips.py`）。

**外部限制**：跑 `batches.py` 與 `prompt.py` 的是系統 `python3`，**沒有 numpy、沒有 PIL**；而 `scripts/ocr/sheets.py` 在模組層就 `import numpy` 與 `from PIL import Image`，切批端不能 import 它。視覺 token 的算法是 `⌈寬÷28⌉ × ⌈高÷28⌉`，寬高可以只讀 PNG 檔頭的 24 個 bytes 拿到（8 bytes 簽章＋4 長度＋4 `IHDR`＋4 寬＋4 高）。

**量出來的數字**（2026-09-11，18 輪實讀、3,367 條 cue，usage 依回覆的 `message.id` 歸併）：尖峰累積 context ≈ `69,184 ＋ 該批視覺 token ＋ 逐逝數 × 17`，對平行讀的六輪誤差 −2.1%～+32.7%；快取失效的界線在 175k–184k（≤175k 失效 0 次；184k 那輪失效 3 次、重寫 166,380 token）。

## Goals / Non-Goals

**Goals**

- 一批的大小由預估累積 context 決定，且各批相當。
- 批裡先讀小圖，讓大圖被重算的次數最少。
- 列批次與寫判準只有一種切法、一份清單。
- 《開會了》同一條 cue 的兩列之間留得比被切掉的降部殘餘還開。

**Non-Goals**

- 不改組合圖的打包規則（寬度、高度上限、排序、裁切都不動）。
- 不改 `sheets.json` 的格式。
- 不為《開會了》寫切批程式。
- 不改讀者判準裡「一則訊息同時發 3–4 個 Read」那條（已落地，且與切批無關）。

## Decisions

### 1. 用最長作業優先分配法（Longest Processing Time first），不用輪流發或連續切塊

三種分法在真實資料上的差別（開會了 111 分 3 批、058晨 分 3 批，模擬逐則回覆的成本）：

| 分法 | 批內順序 | 開會了 111 | 058晨 | 各批負載差 |
|---|---|---|---|---|
| 照檔名切塊（現行） | 原序 | 100% | 100% | 1.44／1.23 倍 |
| 照檔名切塊 | 小到大 | 94.0% | 95.7% | 1.44／1.23 倍 |
| 最長作業優先 | 小到大 | 93.6% | 95.6% | **1.02／1.01 倍** |
| 輪流發（第 k 批拿第 k、k+n… 張） | 小到大 | 93.6% | 95.6% | 1.06／1.07 倍 |

**省錢的是「批內小到大」，不是分法**；分法買到的是各批負載一致。選最長作業優先而不是輪流發，因為輪流發在大小遞增的序列上會讓最後一批每一輪都拿到最大的那張（40 張分 5 批的例子：各批總和 148／156／164／172／180，差 1.22 倍）。最長作業優先是十幾行的貪心，實測各批差 1.01–1.03 倍。

### 2. 每批上限訂 120,000，不是 158,000

快取失效的界線實測在 175k–184k。估算式對平行讀的誤差最大 +32.7%，所以上限訂 120,000 時最壞情形約 160k，離界線還有餘裕；訂 140,000 以上時最壞情形正好落在 175k 的邊上。代價是多切一批（開會了 111 從 3 批變 4 批）。

### 3. 重量用「讀 PNG 檔頭算出的視覺 token」，不用檔案大小，也不寫進 `sheets.json`

檔案大小和視覺 token 的排名相關是 0.988–0.995，拿來**排序、分配**綽綽有餘，模擬費用一模一樣。但**算批數要的是絕對值**：用檔案大小線性換算成 token，逐張誤差中位 3.4%／4.6%、p90 11%、最大 41.8%，而批數是總重量除以上限，估錯就可能讓某一批越過快取失效那條線。讀 PNG 檔頭拿到的是精確值，成本是每張讀 24 個 bytes，所以兩件事都用它。

不寫進 `sheets.json`：那個檔有五支程式在讀，改格式的牽連遠大於讀檔頭。

### 4. 視覺 token 的算法獨立成 `scripts/ocr/sheetsize.py`

切批端沒有 PIL 與 numpy，不能 import `scripts/ocr/sheets.py`。算法只能有一份，否則兩邊會走鐘（`pack-vision-sheets` 已經踩過「常數抄兩份」的坑：`tests/aiyalaeho/test_paths.py` 自己抄了一份 1.10 Mpx 的預算，換規則時兩邊打架）。所以把 `PATCH`、`LONG_EDGE`、`VISUAL_TOKENS` 與 PNG 檔頭讀取放進只用標準函式庫的 `sheetsize.py`，`sheets.py` 改成從它 import。

### 5. 切批回傳「每批的組合圖清單」，判準逐張列出

最長作業優先分完的批在檔名上不連續，`(lo, hi)` 這種表示法承載不了。判準若還寫「第一張–最後一張」，讀者會照檔名範圍去讀到別批的圖——`ingest` 會因為「這條 cue 兩個檔都有」擋掉整集，但那是事後，白讀一輪。

### 6. 兩支程式對同一組組合圖切批，`bNN.tsv` 編號接續

`batches.py` 餵 `pending_sheets()`、`brief()` 餵全部組合圖，是現成的洞：讀到一半之後兩邊的第 N 批不一樣，而且都從 `b01.tsv` 起算，會蓋掉已經收進 Kari-SRT 的檔。改成兩邊都對「還沒核實的組合圖」切（要讀的本來就只有這些），編號則看 Kari-SRT 已經有幾個 `bNN.tsv` 接下去。

### 7. 同一條 cue 的多列，拼回畫面上的樣子——不是把空隙加寬

考慮過「把列與列之間的 2 px 加寬到 6 px」（涵蓋殘餘的 p99）。量下來那是比較差的一條：它讓 111 集的視覺 token 變成 **102.9%**，而且**只是讓那一截比較看得出來是分開的，錯位還在**。

真正的病根有兩層：列窗切在字身上（88% 的 cue 族語列墨水碰到圖條底），以及**兩列各自裁自己的欄範圍**——111 集 976 條實測，兩列左緣差中位 **85 px**、p90 **235 px**、最大 **636 px**，42% 的 cue 差 100 px 以上（cue 804 差 481 px）。所以那一截降部不是落在自己的字母底下，是落在**完全無關的字母底下**，看起來就是那個字母的下加符號。

改成「同一條 cue 的各列用同一個欄裁切範圍（各列墨水的聯集），列與列之間照它們在畫面上的間隔貼」，等於把畫面上那條字幕帶原樣拼回去，兩層病根一起消失。實測：

| 做法 | 張數 | 視覺 token | 每 cue |
|---|---|---|---|
| 現行（各自裁、隔 2 px） | 70 | 152,228（100%） | 155.8 |
| 空隙加到 6 px | 70 | 156,600（102.9%） | 160.3 |
| **拼回去** | 70 | **150,008（98.5%）** | 153.5 |

**拼回去反而最省**：寬度沒有變（兩列的左右跨距中位數都是 708 px——兩列都置中、長度相近，聯集幾乎等於較寬那一列），高度則少掉一個分隔。

實作上不動 preset 的 `lines`、不動 TSV 的列名、不動切 cue：`_cue_blocks()` 現在逐列各自算裁切，改成逐 cue 算一次；`flush_sheet()` 的貼圖游標用同一套規則。**列與列之間的間隔要用「畫面上的間隔」算**（下一列的 `y` 減掉上一列的 `y + h`），《開會了》兩個 preset 都是 0；若某個版型的兩列中間本來就有空白，那段空白要照留，不能一律 0，否則字會擠在一起。

## Risks / Trade-offs

- **量出來的常數會過期**：每批上限 120,000、估算式的 69,184 與每逝 17、快取失效的 175k，都是 2026-09-11 用 18 輪實讀量的，而且讀者有沒有去開原生圖條會讓實際值差 −2%～+33%。換模型、換 harness、或組合圖打包規則再改都要重量。緩解：寫成具名常數並在原始碼註記量法與日期。
- **估算式低估時會逼近快取失效**：三批實測 175k／143k／160k 對預測 132k／131k／131k。上限訂 120,000 是留這個餘裕用的，不能因為「看起來很空」就調高。
- **切批改成整組重新分配之後，續讀時批次內容會全部重排**。這正是編號必須接續、不得覆蓋的原因；`verified.json` 以 cue 編號為鍵，所以進度本身不受影響。
- **判準逐張列出會讓提示變長**：24 張多約 24 行，相對於一批十幾萬 token 可以忽略。
- **拼回兩列會讓《開會了》的視覺 token 少 1.5%**，而且把降部錯位從根上拿掉。《開會了》目前 39 集都讀完了，這一項要到重讀或有新集數才生效。要注意的是它假設「同一條 cue 的各列在畫面上是連著或間隔固定的」——新版型進來時要先量一次再套。
- **本 change 的效益本來就不大**：省錢的大宗（一則訊息讀 3–4 張、一批 24 張）已經落地，這裡是再省 4–6% 加上把尖峰壓穩。若實作中發現牽連比預期大，值得回頭重新裁定範圍。

## Migration Plan

既有工作目錄的 `sheets/` 與 `sheets.json` **不需要遷移**：拼回兩列改的是之後重新打包出來的組合圖，重跑 `cues --sheets` 就會照新規則做。已交付的集數不重跑——`rebuild --verify` 從 `1-cues/` 與 `2-vision/` 離線重建，不碰組合圖與切批。讀到一半的集數在改完之後再派下一批時，批次內容會重新分配，這是預期行為；已經收進 Kari-SRT 的 `bNN.tsv` 不受影響，新批接在後面。

回退方式：把切批改回照張數切塊、把多列改回各自裁切各自貼即可，`sheets.json` 與 Kari-SRT 都沒有欄位變動需要回捲。
